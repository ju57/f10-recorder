# Give the replay module ownership of accepted saves and session retirement

The replay cache/save module owns accepted replay saves and delays disposal of a capture session's files and process resources until all of its accepted saves finish or fail. Capture supervision decides when acquisition stops or a session is replaced; callers do not coordinate pins, snapshots or save polling before cleanup. Keeping the entire old session until export ends uses temporary storage for longer than early reclamation, but makes the lifetime rule straightforward and prevents session disposal from killing an export that still shares its process job.

Stopping acquisition preserves completed footage; retirement rejects new requests and reclaims it after outstanding work finishes. Monitor capture remains continuous across application changes, while restored selected-window capture starts an independent timeline. Publication of the final MP4 establishes save success; notification and temporary-cleanup failures are separate diagnostics.

The original prototype admits one save with no queue. Accepted beta decisions Q9/Q23/Q25 intentionally extend admission to one active export and two waiting requests per recording profile, with earlier rejection when storage cannot be reserved. Export remains serial and FIFO; requests retain their original capture session, source, endpoint, policy and destination. Protect sufficient inputs before pruning, including coverage needed if a preceding new-footage request fails. Only successful final publication advances that session's checkpoint; an old-session save never advances a newer session. There is no automatic retry. This records beta architecture intent; queue implementation and race/resource validation remain mandatory work under the consolidated specification.
