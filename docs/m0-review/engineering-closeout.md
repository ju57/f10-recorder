## Existing profile and settings findings

These are verified source facts, not assumptions about the installed user's settings:

- `Settings` has no schema/version marker and stores a smaller prototype preference set: replay duration/FPS/bitrate/codec, system-audio enable, display index, window executable/class, two output folders and three shortcut bindings. It lacks the accepted manual/microphone/track/cache-budget/indicator configuration. See [Settings.cs:8](../../src/Settings.cs), especially lines 8–27.
- `Load` deserializes, validates and returns a profile. On validation failure it preserves the original in an `.invalid-*` copy, then returns defaults with a conservative window/monitor fallback. That prevents a particular source expansion, but does not implement Q147's field-specific correction while retaining every other valid preference. See [Settings.cs:47](../../src/Settings.cs), lines 47–60.
- `Save` writes a sibling temporary file and uses `File.Replace` or `File.Move`; it does not pass a backup destination. It has no migration journal or cross-file transaction with worker state/startup. See [Settings.cs:61](../../src/Settings.cs), lines 61–66.
- Worker pause/stopped state is a separate JSON file. The worker merges persisted pause at launch and writes a sibling temporary file before replacing the state file. Persistence failure produces a warning. Preserve this distinction rather than treating opening the desktop as permission to start capture. See [RecorderWorker.cs:23](../../projects/F10Recorder.Windows/RecorderWorker.cs), lines 23–29 and 59–73; [WorkerProtocol.cs:67](../../projects/F10Recorder.Windows/WorkerProtocol.cs), lines 67–82.
- Current `ApplyAsync` blocks while saving, validates the engine and shortcuts, disposes the capture engine, saves configuration/startup and starts the engine again. It attempts rollback on persistence/startup failure. It is not the accepted fine-grained live/deferred Apply transaction. See [RecorderHost.cs:109](../../projects/F10Recorder.Windows/RecorderHost.cs), lines 109–136.
- Protocol version 3 and bounded per-user commands already exist. Profile ownership uses protected file leases and canonical identity; preserve those boundaries during migration. See [WorkerProtocol.cs:76](../../projects/F10Recorder.Windows/WorkerProtocol.cs), [ProfileOwnership.cs](../../projects/F10Recorder.Windows/ProfileOwnership.cs), [ADR 0003](../adr/0003-protected-profile-ownership.md).
- Portable checks already contain old-profile preservation, obsolete engine-path removal, invalid-file preservation and clock/selection fixtures. These are useful starting points, not passing evidence for an unimplemented new schema. See [CoreChecks Program.cs:28](../../projects/F10Recorder.CoreChecks/Program.cs), lines 28–43 and [Core project links](../../projects/F10Recorder.Core/F10Recorder.Core.csproj).

Microsoft documents `File.Replace` as file replacement with an optional backup, with cross-volume constraints. `FileStream.Flush(true)` addresses intermediate buffered writes. Neither API reference supplies an application-wide transaction across settings, startup, media publication and worker acknowledgments. Power-loss/rollback behavior therefore needs its own failure-injection evidence; this is an engineering conclusion, not a claimed filesystem durability guarantee. [File.Replace](https://learn.microsoft.com/en-us/dotnet/api/system.io.file.replace?view=net-10.0), [FileStream.Flush](https://learn.microsoft.com/en-us/dotnet/api/system.io.filestream.flush?view=net-10.0), checked 24 October 2026.

## Proposed migration and Apply contract

This is an engineering proposal for review; accepted behavior remains the release plan.

1. Give persisted preferences, pending changes and media/recovery journals explicit schema versions. Keep runtime identities such as HWNDs/PIDs and live missing-device flags out of durable device/source preference identity.
2. Acquire the existing profile lease before reading or migrating it. Preserve original bytes plus version/receipt before replacement. Parse into a migration model that distinguishes a missing field from an explicit `false`, zero or empty value.
3. Preserve valid existing folders, shortcuts, codec, enabled inputs, startup and deliberate pause. Add defaults only for genuinely absent new fields; Full replay follows the already accepted migration default. Do not substitute a different device/display just because the selected one is temporarily unavailable.
4. Migrate pure data before activating capture or registering changed shortcuts. Unknown future schema or unresolvable required fields retain their originals and enter a correction/compatibility state, rather than replacing the entire profile with defaults or repeating full setup.
5. Keep the durable requested generation separate from the actually applied generation. Apply validates the complete proposal, admits required resources and records pending intent before acknowledging that settings were saved. Manual recording defers restart-required work under Q106a/Q152; accepted exports retain their old generation/session/source/destination.
6. Commit applied state only after the native worker confirms it. If activation fails, report actual readiness, preserve accepted work and restore the last working capture/exclusion configuration where possible; retain a diagnosable failed proposal for correction. A worker/UI reconnect must reconcile the generation, not repeat a non-idempotent operation blindly.
7. On upgrade, quiesce only after manual finalization/accepted saves finish, stage a complete package and switch a version pointer with a compatible settings backup. Rollback restores a compatible binary/configuration pair; it must not overwrite media or make retained recovery data unreadable. Unreadable newer recovery state remains preserved for the compatible version.
