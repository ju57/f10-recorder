# M0 engineering research: replay, manual recording, audio, storage and recovery

Checked 24 October 2026 against working-tree source based on commit `fd6fb316b102a8686377f841729469ca70435d09` and the primary sources linked below. This is a design/research result, not an implementation or hardware acceptance report. No recorder, capture, audio endpoint, GPU workload, test suite or installer was started. User decisions through Q157 are requirements; the engineering recommendations below have not been silently promoted to accepted architecture.

## Finding and recommendation

The existing ownership/pinning and common-clock work is a useful foundation, but it does not implement the accepted beta contract. The critical feasibility question is satisfying **both** frame-accurate arbitrary replay boundaries and the accepted five-minute export-speed targets. The current keyframe-aligned stream-copy route deliberately gives up part of the requested interval. Queue/checkpoint, manual recording, retained crash recovery, microphone/two-track audio and reservation accounting require new worker-owned state, rather than additional wireframe states.

Recommend a worker-owned capture-session timeline, immutable encoded segments, independently owned replay/manual consumers, a durable save/recovery ledger and explicit per-volume admission. Prototype exact trimming first, then select shared versus additional encoding using measured results. A coherent plan and admitted feasibility experiments can close M0 design work; they cannot establish M2/M4 recording, sync, performance or recovery acceptance.

## Exact replay boundaries: feasible paths to investigate

FFmpeg's segment documentation describes keyframe-based cuts and rounding tolerance. Its seeking documentation distinguishes accurate transcoding from stream-copy seeking, and concat warns about non-intra in/out points and differing stream layouts. Therefore changing only `segment_time`, `-ss`, `-t`, a manifest duration or the MP4 duration label is not evidence for Q53. [FFmpeg muxer source documentation](https://raw.githubusercontent.com/FFmpeg/FFmpeg/master/doc/muxers.texi), [seek documentation](https://raw.githubusercontent.com/FFmpeg/FFmpeg/master/doc/ffmpeg.texi), [concat documentation](https://raw.githubusercontent.com/FFmpeg/FFmpeg/master/doc/demuxers.texi).

Proposed contract:

1. Capture one QPC trigger and resolve it against the capture epoch, independently of encoder progress and audio availability. Freeze source/session/output profile, requested endpoint, destination and save policy at admission. Represent output boundaries in rational time/frame indices, retaining original timestamps for validation.
2. Retain a preceding decodable GOP as well as the requested interval and the completed tail needed to cover its end. Never use an unfinished input as if it were closed. Pin/reserve those inputs immediately, including inputs whose manifest entries roll out while a request waits.
3. Resolve full replay to available continuous history up to the request, bounded by the configured 1–30 minutes. Resolve new footage against the preceding successfully committed endpoint **in the same session** when its FIFO turn starts; keep accepted endpoint/time unchanged. Less than one second becomes the accepted skipped result, without file/checkpoint advancement.
4. Prototype boundary-only decode/re-encode with compatible copied interior GOPs as the first speed-oriented candidate. Verify codec parameter sets, decode continuity, timestamp rebasing, audio priming/sample boundaries and each advertised codec. This is a candidate, not a claim that arbitrary encoded sections concatenate safely. Use complete interval re-encoding as a correctness comparison; do not silently use a slow fallback to declare the accepted export-speed gate passed.
5. Compare an intra/shorter-GOP acquisition alternative only if it preserves accepted quality/rate, overhead and storage targets. It is not a free fix: its actual encoder cost/quality must be measured. Do not weaken one-frame precision to retain the current fast copy route.

The M0 deliverable is an admitted experiment specification with exact build/profile, arbitrary offsets around GOP/frame boundaries, independent frame IDs, audio markers, closed-input policy and twenty-export cold/warm speed sampling. The implementation must pass both accuracy and speed gates; the research does not establish that it can yet do so.

## Proposed worker state and ownership

Use a profile-scoped coordinator with one export active and at most two waiting replay requests. Admission atomically acquires a queue slot, input lifetime claim and conservative storage reservation; if any cannot be acquired, reject immediately. Do not announce acceptance and later treat capacity rejection as if the request had never existed. Cancellation/failure releases only that request's claims; overlapping requests retain theirs. Old-session requests may finish but cannot move the new session's checkpoint. These proposals implement Q23/Q25/Q28/Q149, rather than changing their policy.

Persist a compact ledger before accepted work can outlive a process: request ID, session ID, frozen endpoint/policy/destination/profile, authoritative input intervals/identities, required tracks, output attempt/commit identity and ownership state. Keep media out of control messages and UI controls. On crash, reconcile ledger and published files without deleting an existing user recording or counting an unvalidated temporary file as success.

Serialize final publication and cancellation under one per-request state machine: `Accepted → Waiting/Exporting → Validated → Committed → Saved`, with pre-commit `Canceled/Failed` paths. Once committed, a late Cancel returns the saved result. Use unique final names and a staging file on the destination volume; cross-volume moves can involve copy/delete, so a cache-volume temporary file must not be treated as a single destination publication step. Flush/journal/reconcile ordering must be tested; a rename alone is not a universal power-loss durability proof. [Windows move semantics](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-movefileexw).

## Manual recording and recovery

Recommend a bounded producer with independently owned replay and manual consumers, not a manual file that relies on the rolling retention window. While replay is paused, a manual consumer keeps acquisition alive; while manual is stopped, replay alone may acquire. Stop all capture ends acquisition before draining/finalizing consumers. Manual inputs remain protected until validated publication or explicit recovery/discard handling. A growing manual session has no replay-duration cap, but must be stopped with a truthful reason before safe finalization resources are exhausted.

Prefer durable closed encoded chunks with an append-only manifest for the first manual/recovery prototype; they align with the existing segment model and allow contiguous valid ranges to be recovered independently. A fragmented-MP4 working file is an alternative to evaluate. FFmpeg documents better interrupted-write/long-file characteristics for fragmented MP4, with a compatibility tradeoff; faststart requires an additional index-moving pass. Neither representation guarantees every damaged tail can be repaired. [FFmpeg muxer documentation](https://raw.githubusercontent.com/FFmpeg/FFmpeg/master/doc/muxers.texi).

Separate disposable replay cache, manual working material, and retained recovery ownership even when they share physical storage. Recovery inputs never enter time-based replay pruning. Apply Q148–Q156: no expiry of retained originals; Cancel preserves inputs; partial output is explicitly partial and retains originals; disjoint valid intervals become separate chronological clips with original ranges/gap disclosure; active recording and accepted saves have priority. Recovery waits with a reason if CPU/GPU/I/O or space admission is unsafe. Do not treat a corruption-tolerant FFmpeg exit code as complete recovery or silently join around missing intervals.

Minimum recovery validation: manifest provenance/path bounds, independent decodability, contiguous source ranges, expected stream schema, actual duration and track-presence disclosures, timestamp ordering and publishability. Validate known silence separately from unknown/corrupt audio. Capture interrupted during manual recording remains stopped until explicit Start. Partial recovery cannot pass ordinary complete-recording qualification.

Publication needs more than the current size check, but **full decoding every saved recording is not the proposed fast runtime path**. Prototype pre-commit structural/packet validation (expected tracks and parameters, readable trailer/index, timestamps/source coverage, expected endpoints, closed-input receipts and boundary decode checks), then measure its cost inside request-to-file time. Freeze which checks run before Saved and what they establish. Independently perform full-file decoding and content/frame/marker checks for qualification; structural validation does not prove every compressed picture decodes or that content A/V alignment passes. Recovery may need deeper scanning to discover usable ranges and therefore has separate resources/priority. Validation scope and latency are a feasibility gate, not a reason to redefine size-only output as valid.

## Storage arithmetic and admission proposal

Use decimal bytes. The payload estimate for duration `T` seconds is:

`payload(T) = T × (video_bits_per_second + sum(encoded_audio_bits_per_second)) / 8`.

The following is arithmetic, **not measured output or a final upper bound**. It assumes two AAC tracks at 192 kbit/s each as a conservative candidate matching the current per-track rate; microphone rate/channel layout is not yet a qualified shipping choice.

| Video rate | 1 minute payload | 5 minutes payload | 30 minutes payload |
| --- | ---: | ---: | ---: |
| 5 Mbit/s | 0.04038 GB | 0.20190 GB | 1.21140 GB |
| 20 Mbit/s | 0.15288 GB | 0.76440 GB | 4.58640 GB |
| 100 Mbit/s | 0.75288 GB | 3.76440 GB | 22.58640 GB |

One 192 kbit/s audio track adds 0.0432 GB over 30 minutes; two add 0.0864 GB. A 30-minute 100 Mbit/s history exceeds the 10 GB new-profile budget **before** container/index overhead, incomplete GOPs, burst allowance or protected snapshots. Therefore Q35 must require an explicit budget increase or lower settings; 10 GB cannot promise every offered profile fits.

Proposed accounting:

- Cache claim = union of live rolling extents, protected old-session/request extents, incomplete/guard segments, actual physical input copies and metadata/scratch. Track shared identities to avoid treating overlapping requests or hard links as independent full payloads. A hard link shares a file on the same volume; it is not a cross-volume copy. Reserve copy fallback unless the selected filesystem/path route has established that linking succeeds. [Windows hard-link semantics](https://learn.microsoft.com/en-us/windows/win32/fileio/hard-links-and-junctions).
- For each actual destination volume, compute `unreserved = caller_available_free - outstanding_future_writes - safety_allowance`. Free space already excludes allocated files; do not subtract their bytes again. Reserve output/finalization and not-yet-created snapshot/scratch bytes, combine same-volume claims and retain separate claims for different volumes. Use volume identity, not drive-letter string equality. `GetDiskFreeSpaceEx` exposes caller-available space, including quota effects and target resolution. [Windows free-space API](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getdiskfreespaceexw).
- Manual working bytes grow with duration; update the future finalization reservation as the recording grows. For a remux-to-new-final-file design, the reserved output can be as large as the entire current manual payload. Do not reserve only one replay window or assume hard links make final output free.
- Bound forecast growth by a measured maximum write/burst envelope and detection/stop latency. A safe stop needs allowance for bytes arriving before the stop takes effect, mux/index scratch and finalization. The existing `1.5` multiplier is not a verified bound. Keep the accepted 5 GB warning/2 GB stop thresholds after reservations, and explicit Resume after safety checks pass (Q150).
- Cache budget is independent of output/manual/recovery free-space claims. Raising it cannot manufacture physical space. If protected usage exceeds a proposed lower budget, reject/defer the decrease with a reason; never delete protected inputs. Retained recovery can legitimately block capture and must link to Recovery rather than auto-expire.

M0 can freeze this accounting model now. Numeric burst/container/scratch multipliers require an admitted sample on the exact shipping engine, quality profiles, filesystems and storage paths. External applications can exhaust space despite prior checks; reservations are application bookkeeping, not an OS guarantee against other writers.

## Audio identity and two-track implementation proposal

Persist separate opaque endpoint IDs for the selected render and capture devices, plus display names for UI only. Resolve with `GetDevice`, not a default endpoint lookup or friendly-name match. Windows documents opaque endpoint IDs and callback-based endpoint changes; callback code must be nonblocking. A device that re-enumerates with a different ID must not silently become the selected device based only on its name. [IMMDevice::GetId](https://learn.microsoft.com/en-us/windows/win32/api/mmdeviceapi/nf-mmdeviceapi-immdevice-getid), [IMMNotificationClient](https://learn.microsoft.com/en-us/windows/win32/api/mmdeviceapi/nn-mmdeviceapi-immnotificationclient).

Use WASAPI loopback for the selected render endpoint and capture mode for the microphone. Loopback captures the render endpoint mix in shared mode; exclusive/protected-source audio needs truthful limitations rather than substitution. [Microsoft loopback recording](https://learn.microsoft.com/en-us/windows/win32/coreaudio/loopback-recording).

Create the video/save acquisition epoch even with no audio. Each device adapter keeps its own sample/device clock mapped into that common QPC epoch. `IAudioCaptureClient::GetBuffer` supplies first-frame device position, QPC in 100 ns units and discontinuity/timestamp flags; arrival time is not the acquisition timestamp. Preserve the existing ordered payload/timestamp approach and test reconnection before accepting an adapter. [GetBuffer](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nf-audioclient-iaudiocaptureclient-getbuffer), [current clock model and limits](/D:/repository/f10-recorder/tests/audio-clock.md:1).

Normalize input formats into a fixed internal rate/layout, apply recorder-owned levels/mute/hold-to-talk, then encode either one mix or two explicitly ordered streams (system first, microphone second). Do not change Windows endpoint volume. For two-track mode, keep the microphone stream and valid silence during agreed disabled/muted/known-unavailable intervals; do not reset video/save epoch or invent synchronized content during untrusted timestamp gaps. Recovery can disclose missing data without claiming normal synchronized output. Test 44.1/48 kHz, mono/stereo, different-clock devices, permitted/denied microphone, same-ID return, USB re-enumeration, default-device changes, slow pipe delivery, no audio and each missing source independently.

### Shared encoding decision

Recommend one normalized acquisition timeline, then a **scoped measured comparison** of separate encoders versus a shared encoded producer for compatible replay/manual consumers. Shared packets are a potential optimization; they are not the selected shipping architecture. Compare exact boundaries, dynamic consumer start/stop, failure isolation, CPU/GPU/memory and the accepted gameplay/sync budgets before choosing. Implement bounded queues and independent sink failure handling; a slow manual writer must not indefinitely backpressure replay, and a replay-pruning decision must never own manual inputs. Do not assume a simple extra FFmpeg output supplies those guarantees.

Q157 makes sharing conditional on resolved output parameters, not merely identical selected preferences. Example: replay starts with Native resolved to canvas A; the source resizes; manual Start resolves Native to canvas B. The active replay retains A while the new manual recording requires B. Reusing one encoded stream must not force manual output onto the stale replay canvas. The comparison must include distinct canvases/encoder schemas, sharing acquisition frames/clock while using separate transforms/encoders when needed. Also test matching canvases where packet sharing may be valid.

Separate encoding has its own GPU/CPU/memory admission and sync/quality measurement costs; no automatic claim of lower overhead is justified for either candidate. FFmpeg supports explicit stream mapping and tee outputs, but that capability is not F10's validated dynamic ownership/scheduling design. [FFmpeg stream mapping](https://raw.githubusercontent.com/FFmpeg/FFmpeg/master/doc/ffmpeg.texi), [tee documentation](https://raw.githubusercontent.com/FFmpeg/FFmpeg/master/doc/muxers.texi).

## Finite closure gates and remaining choices

For M0, approve or replace the proposed timeline/ledger, reservation model, setting classification and measured shared-versus-separate encoding experiment plan. Identify the exact scratch/burst/encoder/validation experiments and their validator before claiming numeric bounds. No further preference question is needed merely to rediscover “preserve saved files,” “do not overwrite” or “report failure.”

Required implementation/qualification evidence remains:

1. Arbitrary-boundary full/new-footage exports at 24/30/60/120 FPS and every advertised codec: independent decode, source-frame coverage, timestamp ordering and <= one-frame boundary/duration rounding, plus twenty-export cold/warm speed samples. Test queue ordering, skip-after-success, failure/cancel checkpoint behavior, session replacement and original timestamps.
2. Failure injection around admission, pin/copy, validation, publication, post-commit ledger update, cancellation, UI/worker crash and cleanup. Exercise same/different volumes, quota/disk-full, copy fallback, existing files and retained originals. Extend ownership checks rather than replacing them. [Ownership checks](/D:/repository/f10-recorder/projects/F10Recorder.WorkerChecks/ReplayOwnershipChecks.cs:155).
3. Two-hour manual plus replay soak with 30-minute history, repeated saves and separately interrupted recovery trials; bound actual storage/memory and verify that replay pause/pruning or UI lifetime cannot end manual recording. Recover multiple contiguous ranges honestly and retain partial originals.
4. Each enabled audio track within the accepted 50 ms alignment/20 ms additional two-hour drift limits, using calibrated coded markers at beginning/middle/end and across device recovery. Compare marker content alignment with container boundaries; neither substitutes for the other. Preserve the existing portable model and actual filter checks as lower-level evidence, not live acceptance.
5. Freeze resource envelopes for each declared quality/storage profile from prospective measurements, including acquisition versus concurrent export versus recovery. Test priority/admission without using a quiet/short run as proof of all supported combinations.

The user need not calculate multipliers, choose a codec implementation from undocumented behavior or provide facts available from source/API documentation. Any new product question should arise from an evidenced tradeoff, for example an incompatibility that would require changing accepted storage-path or quality scope. Such a scope change needs an explicit decision; it is not resolved by this research.
