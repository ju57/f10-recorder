# M0 engineering research: capture, displayed presentation, overlay and FPS

Checked 24 October 2026. This is source/API research against the working tree based on `fd6fb316b102a8686377f841729469ca70435d09`, including uncommitted planning changes. No app, capture session, game, vendor control panel, service or installer was started. No hardware acceptance is established. Primary web sources below were read on this date; upstream `main`/`trunk` documents are not a pinned shipping dependency.

## Recommendation and current confidence

Retain the two explicit capture intents: Desktop Duplication for the selected display, and Windows Graphics Capture for a lifetime-validated selected window. Put a presentation-normalization stage before the session's fixed output canvas, not in Avalonia controls. Keep monitor placement, overlay input and FPS collection independent of capture selection. Existing APIs and source provide starting points, but three risks remain substantial: matching scaling performed after the captured surface, clean overlays coexisting with NVIDIA recording, and interactive visibility over real exclusive fullscreen. None is solved by the HTML review or an encoder capability listing.

| Area | Current evidence | Recommended M0 disposition |
| --- | --- | --- |
| Window identity and no desktop fallback | Existing native target validation and separate window source | Preserve; specify lifecycle/resize regressions |
| Q157 fixed canvas | Window source already requests initial-size aspect fit | Adopt approved rule; extend presented-size determination and presets explicitly |
| Q52 final displayed presentation | No current GPU/monitor transform reconstruction found | Require an evidence-driven transform prototype; do not infer appearance from raw width/height |
| Whole-display clean UI plus NVIDIA coexistence | Historical local incompatibility is documented | Treat as an early architecture gate, not a solved API detail |
| Exclusive-fullscreen capture and overlay | Interfaces can encounter mode changes; ordinary Topmost windows prove neither | Qualify capture, overlay visibility, focus and coexistence separately in real modes |
| Application FPS | Existing benchmark uses PresentMon; product lacks a provider | Prototype a pinned out-of-process provider; keep unavailable truthful |

## API facts and their limits

### Capture, rotation and device loss

Desktop Duplication returns a desktop surface and requires client-side rotation handling. A mode/desktop/fullscreen transition may invalidate acquisition with `DXGI_ERROR_ACCESS_LOST`; the duplication interface then needs recreation. Creation binds a device to the adapter owning the output, and access/session/concurrent-client failures must be handled. These are backend lifecycle facts, not a blanket guarantee for every game's exclusive mode. [Microsoft Desktop Duplication](https://learn.microsoft.com/en-us/windows/win32/direct3ddxgi/desktop-dup-api), [AcquireNextFrame](https://learn.microsoft.com/en-us/windows/win32/api/dxgi1_2/nf-dxgi1_2-idxgioutputduplication-acquirenextframe), [DuplicateOutput](https://learn.microsoft.com/en-us/windows/win32/api/dxgi1_2/nf-dxgi1_2-idxgioutput1-duplicateoutput).

Windows Graphics Capture exposes `ContentSize`, the D3D surface and QPC-based `SystemRelativeTime`. Microsoft recommends copying the valid content rectangle and recreating the frame pool for size/device changes; unused regions can contain undefined data. A direct window capture item is available through `CreateForWindow` from Windows 10 build 18362. These interfaces do not prove the selected game's fullscreen path or F10's A/V correctness. [Microsoft screen capture](https://learn.microsoft.com/en-us/windows/apps/develop/media-authoring-processing/screen-capture), [CreateForWindow](https://learn.microsoft.com/en-us/windows/win32/api/windows.graphics.capture.interop/nf-windows-graphics-capture-interop-igraphicscaptureiteminterop-createforwindow).

Current upstream FFmpeg documents `scale_aspect` as fitting the source into its initial size while preserving aspect ratio. This supports the shape of Q157, but upstream documentation is not proof that the approved engine build behaves identically. Pin and inspect the exact matching source/binary before relying on it. [FFmpeg filter options](https://www.ffmpeg.org/doxygen/trunk/vsrc__gfxcapture_8c_source.html), [WinRT implementation](https://www.ffmpeg.org/doxygen/trunk/vsrc__gfxcapture__winrt_8cpp_source.html).

### GPU scaling is distinct from final monitor appearance

Windows describes centered, stretched, aspect-preserving and custom scaling along the source-to-target display path. Scaling intent does not imply every adapter applies every requested transform. NVIDIA's public interfaces also distinguish GPU and monitor scaling; its support documentation identifies configurations in which monitor scaling is selected and GPU scaling unavailable. Thus raw capture dimensions alone do not establish what a physical panel displays. This last conclusion is an engineering inference, not a measurement on this PC. [Microsoft scaling behavior](https://learn.microsoft.com/en-us/windows-hardware/drivers/display/scaling-the-desktop-image), [DISPLAYCONFIG_SCALING](https://learn.microsoft.com/en-us/windows/win32/api/wingdi/ne-wingdi-displayconfig_scaling), [NVIDIA display controls](https://docs.nvidia.com/nvapi/group__dispcontrol.html), [NVIDIA scaling behavior](https://nvidia.custhelp.com/app/answers/detail/a_id/5694).

Recommendation: construct a per-source presentation descriptor from read-only topology/scaling queries and verified captured-pixel behavior. Its fields should include valid captured rectangle, rotation, source/target extents, presentation transform and confidence. A selected-window transform may alter only that window's pixels; it must never replace the source with a desktop crop. Do not call display-setting mutators or alter the user's NVIDIA/monitor settings to obtain a match. Physical monitor OSD behavior may remain unobservable; a user-confirmed presentation override is a possible fallback requiring a later product decision if the prototype proves it necessary.

Apply transforms in this order: valid source rectangle and rotation; the verified displayed-presentation transform; then fit that presentation into the output canvas frozen at session start. Resolve Native from that initial presentation. Q157 permits padding when the presentation's aspect ratio subsequently changes; it does not authorize undoing visible stretching. A raw 1280×960 surface presented stretched to 1920×1080 must first become that 16:9 presentation, then enter the fixed canvas. This ordering is a proposed implementation design. Exact preset dimensions and even-pixel alignment must be frozen with encoder initialization tests; do not silently use raw window dimensions as the definition of Native.

Q157 also constrains encoder sharing: if replay starts at one Native size, the source later resizes and a new manual recording starts, resolving Native independently at each start can produce different frozen canvases. Shared selected settings do not guarantee identical resolved encoder inputs. The manual/replay architecture must either support that divergence or obtain an explicit clarification before forcing the new recording to inherit an older canvas. This is a design implication of the accepted rule, not a measured encoder cost.

### Clean footage and coexistence are separate gates

`WDA_EXCLUDEFROMCAPTURE` is intended for excluding an application's own top-level controls and is supported from Windows 10 version 2004. Microsoft limits the mechanism to DWM composition/public capture APIs and does not describe it as universal content protection. Affinity success alone therefore cannot qualify the game's capture mode. [SetWindowDisplayAffinity](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setwindowdisplayaffinity).

The repository records a controlled historical observation that visible excluded windows caused NVIDIA protected-content feedback and stopped Instant Replay; ordinary comparison windows did not. That observation is not refreshed here and is not asserted across drivers. It establishes a targeted compatibility question that still needs a current matched test. Selected-window capture avoiding separate F10 windows does not solve monitor-wide clean capture or interactive exclusive-fullscreen visibility. [Local coexistence record, lines 73–84](../ui-specification.txt).

Recommendation: keep exclusion attempts observable, preserve the last working capture policy during failed Apply and make unsupported readiness truthful. Do not ship an ordinary translucent/masked overlay, hide capture silently, disable NVIDIA recording, or switch to selected-window intent as a workaround. Start with an isolated native comparison of ordinary/excluded/no F10 surfaces in each backend; then qualify actual fullscreen. If native composition cannot satisfy the contract, investigate another compositor/capture route as a bounded architecture experiment rather than silently weakening scope. Process injection or UIAccess is not approved by this research.

### Monitor placement, focus and input

`MonitorFromWindow` picks the monitor with greatest intersection and uses the pre-minimize rectangle for minimized windows. Its nearest/primary/null fallback flags do not by themselves implement Q151's last-valid-application memory. `SetForegroundWindow` is restricted and can be denied even when apparent prerequisites hold. [MonitorFromWindow](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-monitorfromwindow), [SetForegroundWindow](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setforegroundwindow).

Recommendation: snapshot a valid external foreground-window identity and monitor at opening, apply the accepted last-valid/primary fallback, and keep that placement for the opening. Use physical monitor rectangles with per-monitor DPI for panel bounds. Handle monitor removal by restoring visibility safely without changing capture intent. Restore focus only if the overlay owns it; an outside click dismisses without being replayed to the application. Passive HUD/notices remain non-activating/click-through. Verify keyboard entry, customized shortcut, Escape, gallery/dialog focus and multi-monitor movement in the native implementation. A Topmost flag is not proof of exclusive-fullscreen visibility.

## FPS provider recommendation

F10 currently has configured output FPS controls, not an application-FPS telemetry provider ([SettingsPanel.cs, line 110](../../projects/F10Recorder.Desktop/SettingsPanel.cs)). The benchmark already uses a pinned PresentMon executable, but that is a test dependency rather than a product integration ([game benchmark, lines 16–20](../../tests/game-benchmark.md)).

PresentMon's project separates ETW collection, console collection and a service/API. Its documentation warns about trace access/group membership and incomplete cross-user process metadata. The service/API has version-compatible loading requirements. Investigate a pinned minimal worker-side collector first; do not launch the whole PresentMon UI or assume a per-user installer can provision a privileged service without an explicit architecture/permission decision. [PresentMon project](https://raw.githubusercontent.com/GameTechDev/PresentMon/main/README.md), [service/API](https://raw.githubusercontent.com/GameTechDev/PresentMon/main/README-Service.md).

The source distinguishes Presented FPS, Displayed FPS and frame types; the release notes separately describe App/Presents/Display rates under frame generation. The accepted counter is application-rendered FPS. Select and validate the application-frame metric for the target process/swapchain, including generated frames, dropped frames, multiple swapchains, minimization and stale-event expiry. Never substitute encoded/captured/output FPS. Use the accepted Unavailable state when permission, target identity or measurement support is insufficient. Measure collection and HUD overhead independently with the feature off/on. [Metric definitions](https://raw.githubusercontent.com/GameTechDev/PresentMon/main/README-CaptureApplication.md), [official release notes](https://github.com/GameTechDev/PresentMon/releases).

## Finite experiments and closure evidence

These are proposed implementation/qualification tasks, not authorization to execute capture. Their resource/time windows and owners must be entered in the repository's experiment contract before live work.

| --- | --- | --- |
| C1: Presentation transform | Coded geometry fixture: raw 4:3 stretched to 16:9, displayed borders, same/different-aspect resize, 90/180/270 rotation, monitor/GPU scaling. Record both known presented appearance and encoded result; verify no desktop pixels enter selected-window output. Fixed canvas and Native start-size remain stable. | Retain evidence; design a verified override or another capture transform. No claimed Q52 pass from dimensions alone. |
| C2: Surface/coexistence | Current driver/build, both backends, ordinary/excluded/no F10 comparison, NVIDIA recording before/during/after, decoded pixel evidence beneath every visible F10 surface. | C3: Real presentation modes | Actual supported games/APIs in windowed, borderless and independently established exclusive fullscreen; capture continuity, UI visibility, focus/Alt+Z/Escape/outside-click, screenshot and HUD exclusion. Include alt-tab/minimize/display loss and elevated-target denial. | Failed mandatory cells remain blocking; borderless success does not substitute. |
| C4: FPS semantics/access | Non-admin clean user, target process/swapchain switches, frame generation, unavailable/stale state and collector stop/restart. Compare the chosen application-frame metric against a controlled rendering fixture. Measure feature-off/on overhead. | Keep unavailable honest; research packaging/permission alternatives. Do not show recording FPS as a substitute. |
| C5: Matrix | Exact Windows build, NVIDIA GPU/driver, adapter topology, monitor scaling/refresh and game build/API/presentation mode captured with the result. | Do not generalize a single-machine observation. |

Use [window-capture qualification](../../tests/window-capture.md), [game benchmark](../../tests/game-benchmark.md), [frame lineage](../../tests/frame-lineage.md) and [experiment admission](../../tests/experiment-contract.md). Decoding, source-picture cadence, content A/V alignment, focus and resource overhead are distinct results; passing one does not establish the others.

M0 can freeze the approved Q52/Q157 rule, explicit capture/backend boundaries, proposed descriptor/canvas pipeline and these named feasibility gates. It cannot honestly close the clean-coexistence/exclusive-fullscreen architecture question from source research alone: an owner and bounded prototype must establish a viable route, with retained failures. Broad matrix acceptance belongs to later qualification, not this research. Remaining user input should be limited to a verified need for a presentation override or an architecture/permission trade-off demonstrated by those prototypes. No cosmetic review is reopened.
