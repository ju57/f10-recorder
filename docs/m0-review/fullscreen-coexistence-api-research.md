# Fullscreen capture and NVIDIA coexistence: public API contracts

Research date: **24 October 2026**. Scope: primary Microsoft and NVIDIA documentation, with PresentMon's own documentation for its diagnostic classifications. This is a documentation investigation, not a measured acceptance result. No game, recorder, capture session, NVIDIA control, installer or live graphics experiment was launched; no user preferences were changed.

## Findings

**Public APIs make fullscreen capture technically plausible, but do not qualify F10's current implementation, interactive overlay, displayed presentation, or simultaneous NVIDIA Instant Replay behavior.** Desktop Duplication explicitly covers fullscreen DirectX content. Windows Graphics Capture (WGC) exposes window and monitor targets. Neither API contract promises compatibility with NVIDIA's independent protected-content policy. These are separate engineering and acceptance questions, not one capability check. Sources and limits follow.

### Desktop Duplication: fullscreen is supported, transitions require recovery

Microsoft's driver documentation explicitly says fullscreen DirectX applications can be duplicated, while protected video remains protected. The capture boundary is an active display. This establishes an API capability, not successful capture of every game/API/driver combination. It also does not turn a monitor target into selected-window capture. [Microsoft: Desktop duplication](https://learn.microsoft.com/en-us/windows-hardware/drivers/display/desktop-duplication-api).

`AcquireNextFrame` can return `DXGI_ERROR_ACCESS_LOST` after desktop switches, display-mode changes, and fullscreen/DWM transitions. The caller must release the duplication interface and recreate it for the new content. `DXGI_ERROR_WAIT_TIMEOUT` is distinct: no new frame arrived within the timeout. Acquisitions can reflect pointer-only changes, so an acquisition count alone does not establish fresh game pictures. Calling again without releasing the previous frame is an invalid call. **F10 implication (inference):** stable entry, exit, Alt+Tab and reacquisition need separate checks; the existence of a recoverable API path is not uninterrupted capture evidence. [Microsoft: AcquireNextFrame](https://learn.microsoft.com/en-us/windows/win32/api/dxgi1_2/nf-dxgi1_2-idxgioutputduplication-acquirenextframe).

Creation has additional constraints:

| Contract | Meaning for feasibility |
| --- | --- |
| The D3D device must belong to the adapter driving the output. | A hybrid or multi-GPU setup needs correct adapter/output selection. |
| One duplication interface per process per output; by default four duplication processes per Windows session. | There is no documented universal single-recorder rule. The limit is not a promise that arbitrary recorder pairs coexist. |
| `DXGI_ERROR_NOT_CURRENTLY_AVAILABLE` signals exhausted duplication capacity. | Preserve the actual HRESULT; do not diagnose every failure as protected content. |
| `E_ACCESSDENIED`, `DXGI_ERROR_UNSUPPORTED`, and `DXGI_ERROR_SESSION_DISCONNECTED` cover different conditions. | Secure-desktop privilege, unsupported modes/scenarios, and session disconnection need distinct handling. |

The creation documentation lists unsupported non-DWM desktop modes, while the driver overview explicitly supports fullscreen DirectX duplication. Read these together: neither a blanket ban on fullscreen nor a universal success guarantee follows. [Microsoft: DuplicateOutput, return values and remarks](https://learn.microsoft.com/en-us/windows/win32/api/dxgi1_2/nf-dxgi1_2-idxgioutput1-duplicateoutput).

`DuplicateOutput1` adds a supported-format list. It can return a fullscreen application's original back-buffer format instead of `DuplicateOutput`'s BGRA conversion; this can avoid conversion cost and retain higher color gamut. Include `DXGI_FORMAT_B8G8R8A8_UNORM`; DXGI can convert when the running buffer format is absent from the supported list. Its documented error cases still include incorrect adapter, duplicate output in the same process, access denial, unsupported scenario, exhausted concurrent duplication capacity and disconnected session. **Limit:** format negotiation does not establish an HDR-correct encode pipeline or reproduction of all GPU/display scaling. [Microsoft: DuplicateOutput1](https://learn.microsoft.com/en-us/windows/win32/api/dxgi1_5/nf-dxgi1_5-idxgioutput5-duplicateoutput1).

### WGC: window/display selection, capture border and minimized windows

WGC acquires frames from an application window or display. The documented picker route shows system selection UI and a capture-indicator border. `GraphicsCaptureSession.IsSupported()` is the platform support check. Resizing/device changes require frame-pool handling; the documentation recommends `Recreate`. **Limit:** a successful support query or capture-item creation does not prove fresh pictures from a particular exclusive-fullscreen game. The reviewed overview does not supply that blanket guarantee. [Microsoft: Screen capture](https://learn.microsoft.com/en-us/windows/apps/develop/media-authoring-processing/screen-capture).

For Win32 interop, `IGraphicsCaptureItemInterop::CreateForWindow(HWND, ...)` creates a window target and is documented from Windows 10 version 1903/build 18362. [Microsoft: CreateForWindow](https://learn.microsoft.com/en-us/windows/win32/api/windows.graphics.capture.interop/nf-windows-graphics-capture-interop-igraphicscaptureiteminterop-createforwindow). `CreateForMonitor(HMONITOR, ...)` supplies the corresponding monitor target with the same documented minimum build. [Microsoft: CreateForMonitor](https://learn.microsoft.com/en-us/windows/win32/api/windows.graphics.capture.interop/nf-windows-graphics-capture-interop-igraphicscaptureiteminterop-createformonitor). **F10 implication (inference):** window capture and display capture are different privacy boundaries. A failed window target cannot silently justify capturing the whole display.

`IsBorderRequired = false` is not sufficient by itself to suppress the system border. Microsoft documents user consent through `GraphicsCaptureAccess.RequestAccessAsync(Borderless)` and a `graphicsCaptureWithoutBorder` package capability. If permission is denied, setting the property can succeed but be ignored; another app requiring a border for the same item can keep it visible. The property documents API contract v12/build 20348 availability. **Limit:** border suppression is version/consent/package sensitive; it is unrelated to excluding F10's UI from captured pixels or reproducing NVIDIA's in-game overlay. [Microsoft: IsBorderRequired](https://learn.microsoft.com/en-us/uwp/api/windows.graphics.capture.graphicscapturesession.isborderrequired?view=winrt-26100).

Microsoft's Win32 WGC sample explicitly notes that minimized windows are enumerated but not captured. Treat it as first-party sample behavior, not an exhaustive description of every future capture option. **F10 implication (inference):** enumeration and a live HWND cannot establish usable acquisition while minimized; qualify the exact implementation and report unavailable/stale input rather than inventing continuous gameplay. [Microsoft: ScreenCaptureforHWND sample](https://github.com/microsoft/Windows.UI.Composition-Win32-Samples/blob/master/cpp/ScreenCaptureforHWND/README.md).

### Capture exclusion: scoped OS behavior, not an NVIDIA compatibility promise

`SetWindowDisplayAffinity` requires a top-level window owned by the caller. `WDA_EXCLUDEFROMCAPTURE` (`0x11`) makes the window absent from covered capture output; `WDA_MONITOR` leaves it without content elsewhere. The exclusion value is supported from Windows 10 version 2004; earlier systems treat it as `WDA_MONITOR`. The feature works when DWM composes the desktop and covers a specific set of public OS capture features/APIs. Microsoft explicitly distinguishes it from a security guarantee or DRM. Failure returns `FALSE`, with extended information from `GetLastError`.

**F10 implication (inference):** a successful call establishes that Windows accepted this request for this window. It does not establish exclusion by every capture implementation, invisibility over true exclusive fullscreen, permission to modify other processes' windows, or coexistence with NVIDIA App. [Microsoft: SetWindowDisplayAffinity](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setwindowdisplayaffinity).

NVIDIA documents that Instant Replay with **Desktop capture enabled** can fail to start or stop when NVIDIA App detects copy-protected content in an open application. Its examples include streaming services and certain games with aggressive anti-cheat. This is a vendor application policy beyond a successful Microsoft capture API call. The KB does not identify `WDA_EXCLUDEFROMCAPTURE` as its precise detection mechanism. [NVIDIA KB 5602: Instant Replay desktop capture stops](https://nvidia.custhelp.com/app/answers/detail/a_id/5602).

NVIDIA separately documents Discord streaming disabling Instant Replay when Desktop capture is enabled and discusses detection of a copy-protected flag. Its published workaround changes Desktop capture settings. **Research limit:** this is evidence that simultaneous applications can interact with NVIDIA's policy; it is not an F10 reproduction, a documented mapping from WDA to NVIDIA internals, or proof of a fix. No workaround/settings change was performed. [NVIDIA KB 5664: Discord streaming and Instant Replay](https://nvidia.custhelp.com/app/answers/detail/a_id/5664).

**Conclusion from these contracts (inference):** switching F10 from Desktop Duplication to WGC cannot, by itself, establish NVIDIA coexistence. Capture choice, UI affinity, NVIDIA Desktop capture state, protected-content detection, and encoder/resource capacity are separate variables. No reviewed source promises that WGC, a hidden capture border, successful affinity, or two successful duplication clients bypass NVIDIA's policy. The README's historical local comparison remains a separate local report; this research does not refresh it or establish its internal cause.

### Establishing actual exclusive mode

A game's **Fullscreen** menu label and a borderless monitor-sized HWND are insufficient. Microsoft explains that Fullscreen Optimizations can make a game believe it is exclusive while Windows runs an optimized borderless presentation. Showing overlays can also return control to desktop composition. Therefore qualify the measurement interval itself, including what happens when F10 surfaces appear. [Microsoft: Demystifying Fullscreen Optimizations](https://devblogs.microsoft.com/directx/demystifying-full-screen-optimizations/).

Independent Flip is also insufficient as exclusive-mode evidence. Microsoft's flip-model guidance says a windowed application's frames can bypass composition and go directly to the display through DirectFlip/Independent Flip, including scaling and MPO variants. A sleeping DWM or fullscreen-like performance is consequently not conclusive ownership evidence. Microsoft links PresentMon as a way to inspect the presentation path. [Microsoft: DXGI flip-model guidance](https://learn.microsoft.com/en-us/windows/win32/direct3ddxgi/for-best-performance--use-dxgi-flip-model).

For a task-owned fixture whose swap chain is available, record the actual `GetFullscreenState` result and target output, not just the requested `SetFullscreenState` value. The query returns full-screen/windowed state associated with that swap chain. **Limit:** it is not an API for querying an arbitrary foreign HWND's swap chain, and the reported API state alone does not resolve FSO's actual presentation path. [Microsoft: GetFullscreenState](https://learn.microsoft.com/en-us/windows/win32/api/dxgi/nf-dxgi-idxgiswapchain-getfullscreenstate).

API selection matters: Microsoft's current Direct3D 12 documentation states that D3D12 does **not** support FSE and that `SetFullscreenState` does not enter FSE; it changes display configuration to allow fullscreen optimizations. A D3D12 fixture is therefore not sufficient qualification for legacy true exclusive fullscreen. [Microsoft: D3D12 swap chains](https://learn.microsoft.com/en-us/windows/win32/direct3d12/swap-chains). NVIDIA's swap-chain guidance also uses the term **true immediate independent flip** for a D3D12 path involving `SetFullScreenState(TRUE)`; that terminology must not be relabeled as legacy FSE. [NVIDIA: Advanced API Performance, Swap Chains](https://developer.nvidia.com/blog/advanced-api-performance-swap-chains/).

Proposed evidence method, **not executed here**:

1. Record Windows build, GPU/driver, game/build, renderer, display configuration, requested mode and existing FSO/NVIDIA state without changing the user's preferences. Use an FSE-capable renderer for a claim about legacy FSE; record API state from a task-owned fixture when available.
2. Retain a presentation trace tied to the game's actual process/swap chain for a quiet baseline, capture start, F10 UI visibility, Alt+Tab/return and fullscreen exit. Do not infer the whole run from one stable sample. Record transitions and missing/unclassified intervals.
3. Interpret classifications using the exact diagnostic tool/version: PresentMon documents `Hardware: Legacy Flip` as application screen ownership; `Hardware: Independent Flip` explicitly lacks screen ownership; `Hardware Composed: Independent Flip` identifies an overlay plane. Legacy copy-to-front-buffer is another ownership path. Combine this trace with renderer/API/context evidence; unclassified or lost trace data makes the claim inconclusive. [PresentMon: console classifications](https://github.com/GameTechDev/PresentMon/blob/main/README-ConsoleApplication.md).
4. Compare the picture and timeline separately: fresh game identities, entry/exit recovery, replay continuity, displayed scaling/borders, cadence and A/V behavior. Separately establish whether NVIDIA stays enabled **and actually continues acquiring/saving fresh footage**. A lit toggle, successful HRESULT, valid MP4 container, or visible overlay establishes none of the other properties.

The last step is an F10 acceptance proposal rather than an external API guarantee. It must follow the repository's experiment admission and test-effects agreements and needs separate authorization before live game/capture work. Observer overhead must be reported. A borderless/Independent Flip pass may be useful but cannot close a true-exclusive requirement.

## F10 decision boundaries

- **Supported direction:** investigate fullscreen monitor capture and transition recovery without assuming a game hook is required. Desktop Duplication's public contract permits this direction.
- **Unresolved direction:** exact selected-window behavior in genuine exclusive mode, UI visibility without disturbing that mode, fidelity to display scaling, and simultaneous NVIDIA recording must each be qualified for the intended platform/game matrix.
- **Do not promote as established:** a WGC migration, capture exclusion, disabled border, successful NVENC/duplication initialization, or FSO/Independent Flip test as a solution to all fullscreen/coexistence requirements.
- **Local scope:** this note changes no accepted design or ADR. In particular, [ADR 0006](../adr/0006-match-displayed-presentation.md) still requires the displayed presentation, including intentional stretching and existing borders; an API's source surface/format alone does not establish that acceptance.
