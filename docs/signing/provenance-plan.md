## Exact coverage proposal

This is a **path/ownership policy**, not an inventory measured from a finished package. Generate the exact per-version file list and hashes from hosted outputs before approval. Unknown files fail the allowlist review.

| Artifact / source | Proposed operation | Required evidence / unresolved boundary |
| --- | --- | --- |
| `F10Recorder.Desktop.exe` apphost, shipped as `F10Recorder.exe` by current installer | Sign approved shipping app executable once; preserve bytes/signature across rename. | Host-generated stub plus project metadata: confirm Foundation treatment, exact SDK origin and file metadata. Do not sign both names as different products. |
| `F10Recorder.Desktop.dll`, `F10Recorder.Windows.dll`, `F10Recorder.Core.dll` | Include these F10-owned compiled PE assemblies in explicit signing scope, subject to provider configuration. | Source-to-output mapping, product/version metadata and signature checks. Cached externally signed uninstallers must retain exact provenance and invalidate when builder/settings change. |
| `ffmpeg.exe`, `ffprobe.exe` and other Gyan payload | Bundle approved upstream bytes only; **do not re-sign under F10's subscription**. | Preserve hashes/signatures if any, notices, exact source/build/license mapping. A signed container does not make these F10-owned code. |

ZIP/SHA-256 alone is not a code-signing certificate; script signing requires a separate explicitly approved policy if scripts ship. |

## Proposed pipeline, after separate implementation authorization

1. **Freeze reviewed source.** Resolve an immutable repository commit, release version, protected release ref policy and reviewed dependency/build/installer inputs. Include workflow files and any generated code. Record provider acceptance/configuration separately. A tag alone is mutable unless controlled and resolved to its commit.
2. **Hosted origin.** Build and all jobs leading to the signing request use GitHub-hosted agents. Use a clean checkout, pinned action revisions, locked RID-specific restore, approved dependency hashes and recorded actual SDK/runtime/builder versions. Hardware acceptance uses separately controlled evidence bound to the candidate, not a local binary replacing the hosted artifact. The documented connector requires an uploaded GitHub artifact ID and verifies provenance; provider policy must enforce it. [GitHub connector](https://docs.signpath.io/trusted-build-systems/github).
3. **Inventory before signing.** Enumerate files with relative path, size, SHA-256, owner/source revision, license/source link, upstream signature status and proposed signing treatment. Reject missing/extra files, wrong product/version and modified upstream bytes. Set `F10` product attributes consistently and one agreed release version, while preserving dependency versions. Preserve internal project/executable/folder identifiers and dependency versions; the public-name decision does not rename them. Review actual compiled PE fields and configure provider metadata restrictions; declaration in a project file is insufficient.
4. **Submit approved app payload.** Upload the immutable unsigned artifact using the supported artifact action and submit that artifact ID through the trusted connector with a restricted CI account. Trusted-build verification disallows interactive-user submitters. Record run ID/attempt, source commit, artifact ID/digest, upload/download hashes and provider request/configuration IDs. Refuse local/manual unsigned uploads as a substitute for hosted source provenance. Keep PR/untrusted-fork execution away from signing secrets and authorization. Product APIs are capabilities, not proof a free subscription enables any requested configuration. The documented GitHub App requirement for audit-log evaluation is not asserted as a universal basic public-repository integration requirement; confirm the chosen configuration's access needs.
5. **Human signing decision.** The confirmed approver checks revision/reviews, gates relevant to this candidate, component manifest, metadata and origin, then manually approves the specific request. No automatic release approval on green CI, no blanket future version authorization. App signing and any required installer/uninstaller requests each follow the accepted provider policy.
6. **Package without source substitution.** Verify returned signed payload against its expected manifest and authenticated changes; build the offline per-user Inno installer from those bytes. Resolve the uninstaller signing exchange on hosted runners and retain request/cache identities. Upload and sign the final installer through its own verified-origin request. Confirm the provider supports this two-stage lineage before implementing around it; do not treat a signed download as automatically trusted source input.
7. **Verify and qualify final bytes.** Verify each intended PE/installer/uninstaller Authenticode signature, trust chain, expected publisher and timestamp under the accepted validation policy. Compare all non-signing content and preserved upstream hashes, inspect installer contents and test the exact installed payload in authorized clean environments. Wrong publisher, tampered payload, missing required signature, wrong version, unavailable signer or rejected provenance must block publication. Test a known-good control and consequential rejected cases; a successful signing API response is insufficient.
8. **Freeze release receipt.** Record final signed hashes, version/source/dependency/source-distribution manifest, hosted run/artifact/request IDs, human approval and all gate evidence. Signing changes hashes: attach exact-candidate acceptance to final signed bytes and document any justified unchanged-code evidence reuse. ju57 then decides publication separately. No mutation/repacking after final signature; changed bytes require affected checks again.

Minimum proposed receipt fields: schema/version; source commit/ref; review references; builder/SDK/action revisions; lock/input hashes; unsigned artifact ID/digest and file manifest; provider org/project/policy/config revision and request IDs; approver/time; final artifact hashes/signature subject/chain/timestamp verification; package-source/notices links; exact test commands/results/limits; immutable gate evidence. Secrets, raw account/security exports and private contacts are excluded.

## Consequential validation cases for later integration

| Case | Expected observable result |
| --- | --- |
| Approved hosted commit/version and complete owned-file allowlist | Origin accepted, required signatures verified and every upstream hash preserved; publication still awaits release approval. |
| Identical filename replaced with local or different-run artifact | Origin/manifest rejection; no signing or release approval inferred. |
| Extra upstream DLL or FFmpeg included in signing selection | Allowlist/configuration rejection before it can receive the F10 certificate. |
| Wrong product/version; unsigned required uninstaller; changed installer after signing | Metadata/signature/package validation fails and blocks release. |
| Provider unavailable/rejects request; no human approval | Remain unsigned/unreleased; retain failure receipt and invoke maintainer decision trigger when applicable. |

These are planned cases; none was executed in the documentation lane. Hosted signing provenance does not qualify capture, A/V, GPU performance, installation or all 12 release gates.
