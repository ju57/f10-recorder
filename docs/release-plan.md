# Windows + NVIDIA public beta release plan

Date: 20 October 2026; planning decisions consolidated through Q158 on 25 October 2026 (Europe/Lisbon). Original planning baseline: `e8713db24a7476b0e7db71548ae69b75c57886af`; security implementation baseline: `692c4dfd6d50ff0062c51947c1c5351ee01ca7de`.

**Status: M0 planning complete under Q158, 25 October 2026.** The [versioned consolidated spec](beta-spec.md), published as [issue #10](https://github.com/ju57/f10-recorder/issues/10), records accepted behaviour and an owned mandatory release-gate register. M1–M5, implementation and binary-release qualification remain open. This planning document authorizes no implementation, live capture, installation or public binary release. PR #4 integrated the five security remediations and screenshot-binding fix; remaining verification and final-candidate review still gate distribution. The separately agreed [workflow improvements](agents/workflow-improvements.md) are implementation work, distinct from authorization to release binaries.

## 1. Release goal and scope

Release a Windows + NVIDIA beta that lets people save recent gameplay or record a whole session, with clear controls, predictable audio and safe storage. Linux follows in a separate release. Retain C#/.NET, Avalonia and the independent recording worker; rebuilding the interface does not require replacing the application stack.

Agreed scope:

- Rebuild the desktop interface, interactive overlay, system tray context menu, recording indicator and notifications as one consistent experience.
- Add manual Start/Stop recording, named display selection, output resolution choices and essential audio controls.
- Make instant replay substantially faster to save without interrupting capture or damaging footage.
- Offer both full rolling-window saves and saves containing only new footage since the preceding successful replay save.
- Provide an installer, security remediation, dependency compliance, release qualification and an external feedback process.

The confirmed default for replay saving is **Full replay each time**, preserving the overlapping-save behavior requested in planning and for existing profiles. The alternative is **Only new footage after the previous replay save**, enabled by explicit user choice. Both are beta requirements. Existing recording preferences and saved media must survive upgrades; remaining new-user defaults and migration details must be specified before implementation.

Later scope: Linux X11/Wayland capture and packaging, per-application audio isolation, automatic highlights, game profiles, trimming and broader HDR support. Streaming, webcam composition, filters, driver management and a large performance dashboard are outside this beta. A basic recent-captures view is in scope; a full editor is not.

Use ShadowPlay as a workflow reference, implementing features independently. Do not ship NVIDIA code, icons, fonts or extracted resources. Full NVIDIA feature or performance parity is not a beta promise.

### Clean footage and coexistence

Display capture records what is on a display, so visible F10 controls would normally enter the footage. Windows can mark those controls as excluded from recordings. Earlier controlled local observations found that showing such a window made NVIDIA report protected content and stop Instant Replay. Ordinary windows did not. The precise NVIDIA internals and behavior on other drivers remain unknown.

Application capture can record only the selected application's picture while leaving F10's separate windows outside it. Current application mode therefore uses ordinary F10 windows. This changes capture semantics and does not automatically establish fullscreen, synchronization or recovery acceptance.

Release criteria:

- Declare supported display/application capture and game presentation modes. Windows + NVIDIA true exclusive fullscreen and borderless fullscreen are beta requirements in both whole-display and selected-application capture, alongside windowed use; do not silently narrow this to Windows 11, borderless-only or a single capture path. Freeze exact OS versions and the game/GPU/driver matrix, and qualify the promised combinations before release. Broader HDR support remains deferred; unqualified combinations are identified before use.
- Showing settings, overlay, HUD or notices preserves underlying gameplay pixels and recording continuity in every supported combination. No black replacement masks or silently hidden acquisition gaps.
- F10 does not unexpectedly stop another recorder in a combination advertised as supported, and never changes NVIDIA settings automatically. A warning alone is not proof of coexistence. If clean display capture and coexistence cannot both be qualified, change the design or explicitly narrow supported combinations before releasing.
- New profiles default to the primary monitor; application capture is an explicit alternative. The source selector names displays and identifies them visually; it does not expose raw adapter indices as the main user interaction. Reordering/disconnection preserves intended source identity or asks the user to reselect. Upgrades preserve existing recording preferences.
- In selected-window mode, minimize/close stops acquisition from the target, retains completed footage and shows Application unavailable. Never fall back to the desktop or silently record black frames. Restoring the original window can resume replay in a fresh session; selecting a replacement requires user action. A manual session forced to end follows the interruption/recovery policy. In whole-display mode, closing or minimizing a foreground application does not stop recording the screen or reset its session/checkpoint. Readiness, retained footage and a newly filling buffer remain distinguishable; ambiguous window identity cannot broaden capture.
- Settings apply/rollback, screenshots, focus return, Escape and UI reconnection are tested against actual captures, not just UI screenshots or successful API return values.

## 6. Replay-save behavior

### User-selectable policies

The replay duration is configurable from **1 to 30 minutes**, defaulting to **five minutes** for new profiles while preserving existing configured durations. Once that much continuous footage is available, full-replay mode must export the configured duration ending at the request: five minutes means the last five minutes, thirty means the last thirty. The examples below use five minutes. A successful save does not empty the buffer or stop capture in either mode. The separately agreed new-footage mode still saves only the available footage since its successful checkpoint, capped by configured rolling retention.

### Boundary, queue and failure contract

- **Request time:** the shortcut/button press defines the end of the requested footage, not the time a queued export eventually starts. An accepted request retains its source, capture session, save mode and endpoint across settings changes and protects the necessary retained inputs until export finishes or is explicitly cancelled. A closing segment may finish after the press; export still uses the request's boundary. Later settings affect subsequent requests.
- **Continuous buffer:** pinning/snapshot protection prevents pruning a save's inputs; rolling capture and later saves continue. Do not use `-segment_wrap`, consume the replay history on save, or lower capture quality to make export look faster.
- **Coverage checkpoint:** track the actual end of successfully committed replay files in either save mode for this profile and continuous capture session. New-footage mode reuses this checkpoint when only the save mode changes. It advances only after a valid final file is committed, never on acknowledgement, queue insertion, cancellation or failure. A different capture session starts with no successful checkpoint of its own.
- **Rapid saves:** allow one active export and two waiting requests per profile, in request order. Show the waiting count and reject further requests immediately with Save queue full; storage admission can reject requests sooner under Q35/Q36's cache budget and per-volume free-space reserves. Freeze conservative byte/scratch estimates before implementation. Explain accepted, queued and rejected requests immediately. Rejected requests do not move the checkpoint. Avoid unlimited exports competing with capture.
- **Queued new-footage saves:** reserve enough input at acceptance to handle an earlier queued save failing. Resolve each request's start against the last successful checkpoint when its turn executes. A later request must not silently assume that failed predecessor footage was saved.
- **No new footage:** require at least one second of available/new footage for a save. Below that threshold, explain Not enough new footage yet, create no empty/duplicate file, claim no success and do not advance the checkpoint. Define the handling of accepted queued requests that resolve below this threshold in the remaining error-flow work.
- **Warm-up:** allow a clearly labelled save of available history when at least one second but less than the configured duration exists, without padding or implying a full buffer. Show available versus configured duration: for example, two of thirty minutes available. Once full, apply the exact configured-duration requirement.
- **Long gap:** if eight minutes have passed since the preceding save and only five minutes remain, new-footage mode can save those five minutes. State that the intervening three minutes have expired; do not imply that all eight were preserved.
- **Restart or discontinuity:** never join unrelated timelines. Confirmed by Q22b: a different capture session starts a fresh checkpoint; its first new-footage save uses available footage from that session and establishes a checkpoint only on success. Switching capture source or a genuine capture restart starts a different session. Monitor capture remains continuous across foreground-application changes. Paused replay retains completed footage for saving; resume starts a fresh buffer/session/checkpoint. Accepted old-session requests retain their original identity and can finish, but cannot advance a new session's checkpoint. Freeze exact session-boundary behavior during device/display changes and resource bounds for retained old-session work before implementation.
- **Mode change:** confirmed by Q22a: changing only the replay-save mode preserves the existing capture session, buffer, files and checkpoint. Entering new-footage mode uses the most recent successfully saved replay endpoint from that session, even if that replay was saved in full mode. Without a successful checkpoint, its first save uses available rolling history.
- **Cancellation:** users can cancel queued or not-yet-completed exports. Report Canceled without advancing the checkpoint, preserve inputs needed by remaining requests and keep buffering/manual recording running. An already completed clip remains saved. Qualify cancellation/publication races and recomputation of later new-footage requests; explicit cancellation is separate from timeout.
- **Video boundaries:** current full-window selection may be roughly one second short because it starts at a safe decoding boundary. Q8 requires the configured 1-30 minute duration once sufficient continuous history exists, and Q53 permits at most one output frame of boundary/duration rounding; do not carry the old shortfall into the beta contract or substitute padding/altered duration metadata for requested footage. Assess actual source coverage and frame/audio timing separately from reported container duration. Freeze frame accounting, audio/container granularity, new-footage overlap/gaps and implementation while retaining the accepted five-minute save-speed targets.
- **Failure/quit:** disk-full, missing source, queue cancellation, worker failure and shutdown preserve existing clips, release task-owned pins safely and never expose a partial file as a successful result. Pending work and unsaved coverage are visible to the user.
